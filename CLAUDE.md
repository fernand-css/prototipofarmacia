# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Proyecto

MVP en Django 5.2 del sistema de turnos de la **farmacia del CESFAM San Nicolás** (Chile). Código, plantillas, mensajes y commits están en español; mantén ese idioma. El README describe el MVP completo (tickets, pantalla de sala de espera, panel de atención, historial), pero hoy existen las apps `cuentas` (spec 01), `turnos` (spec 02: tótem, cola ponderada, ventanillas y panel de atención; spec 03: pantalla pública de la sala de espera con anuncio visual y por voz; spec 04: importación del padrón y recetas vigentes desde un archivo de Rayén y avance de cada receta; spec 05: preparación de cada atención, preparados pendientes de retiro y espera estimada en el ticket) y `reparto` (spec 06: domicilios de los pacientes con despacho a domicilio, con mapa, fotos y verificación en terreno, HU-12). Quedan para specs posteriores el panel de mermas (HU-20) y el resto del reparto: asignar, consultar y registrar entregas (HU-13 a HU-16), notificaciones y confirmación del paciente (HU-19 y HU-22) y el modo sin conexión (RNF-03).

## Comandos

```bash
pip install -r requirements.txt     # Django, asgiref, sqlparse, tzdata, openpyxl (y et-xmlfile), Pillow
pip install -r requirements-dev.txt # además django-extensions, Werkzeug y pyOpenSSL: HTTPS de desarrollo
python manage.py migrate
python manage.py runserver          # http://127.0.0.1:8000/
python manage.py runserver_plus 0.0.0.0:8443 --cert-file certs/dev.crt   # HTTPS en la red local (GPS del teléfono); con TURNOS_HOSTS_LOCALES=<ip>
python manage.py test               # cuentas/tests.py y los paquetes turnos/tests/ y reparto/tests/ (~7 s)
python manage.py test cuentas.tests.RolesTests.test_qf_crea_un_encargado_de_terreno   # un solo test
python manage.py test turnos.tests.test_motor                                          # un módulo de pruebas
python manage.py test turnos.tests.test_motor.MotorTests                               # una sola clase
python manage.py createsuperuser    # pide RUT, nombres, apellidos y contraseña
python manage.py cargar_datos_demo  # 4 ventanillas, pacientes/recetas simulados (Rayén) y 30 atenciones de días anteriores y 2 domicilios a nombre de la primera QF; idempotente, no para producción
python manage.py generar_padron_sintetico --salida padron.csv   # o .xlsx; 670 pacientes y 10 filas inválidas, --semilla 1
node --test "pruebas_js/*.test.js"  # funciones puras de static/js/sala.js y reparto.js (coordenadas y distancia); Node 21 o superior, sin dependencias
```

Las pruebas de `turnos` están en `turnos/tests/`, un módulo por área (`test_modelos`, `test_emision`, `test_totem`, `test_motor`, `test_ventanillas`, `test_llamado`, `test_atencion`, `test_cola`, `test_sesion`, `test_sala`, `test_importacion`, `test_padron`, `test_recetas`, `test_preparacion`, `test_estimacion`); lo que comparten (`crear_usuario`, `crear_paciente`, `dejar_lista`, `LlamadoTests`...) está en `helpers.py`. Desde el spec 05, finalizar una atención exige la preparación lista: en las pruebas, `dejar_lista(usuario)` la marca antes de `finalizar_atencion`. Las de `reparto` están en `reparto/tests/` (`test_modelos`, `test_servicios`, `test_fotos`, `test_vistas`, `test_ficha`, `test_mapa`, `test_demo`); las que escriben fotos usan un `MEDIA_ROOT` temporal **por prueba**, porque deshacer la transacción no borra los archivos del disco. Al correr `manage.py test`, `settings.py` cambia a un hasher de contraseñas rápido (`PASSWORD_HASHERS` con MD5, solo en pruebas): con el de producción cada `create_user` tardaba ~0,4 s y la suite ~2 min.

Para probar a mano: `migrate` + `cargar_datos_demo` + `runserver`, y abrir `/totem/` (público) junto a `/atencion/` con una cuenta de funcionario, y `/sala/` en una ventana privada (sin sesión).

No hay linter ni build configurados. El `venv/` del repositorio se creó en otro equipo (su `pyvenv.cfg` apunta a un Python que no existe aquí) y está en `.gitignore`: si no arranca, créalo de nuevo con `python -m venv venv` en vez de repararlo. `db.sqlite3` también está ignorado.

## Flujo de trabajo por specs

El trabajo se organiza en `specs/NN-nombre.md` (alcance, modelo, plan, criterios de aceptación, decisiones y riesgos), con una rama por spec (`spec-01-autenticacion-y-cuentas`, `spec-02-totem-cola-ponderada-y-ventanillas`, `spec-03-pantalla-de-sala-y-anuncio-de-llamados`, `spec-04-importacion-del-padron-y-recetas-vigentes`, `spec-05-preparacion-pendientes-de-retiro-y-espera-estimada`, `spec-06-domicilios-de-pacientes-con-despacho`). Lee el spec correspondiente antes de implementar. No hay índice de specs: el spec 02 reservaba el 03 para la estimación de espera y las recetas, pero el 03 terminó siendo la pantalla de sala y mandó esos temas (y las mermas) al 04 o posteriores. El 04 terminó siendo la importación del padrón (HU-23) y el cierre de HU-21, y la estimación de espera (HU-18), los preparados pendientes de retiro (HU-17) y las mermas (HU-20) pasaron juntos al 05 o posteriores, porque los tres necesitan registrar cuándo una receta queda preparada. El 05 hizo HU-17 y HU-18; las mermas (HU-20) van en un spec propio. El 06 empezó el módulo de reparto con HU-12 y está implementado, salvo lo que sacó el equipo durante la implementación: **las columnas de domicilio en la importación del padrón** (su paso 7) y el padrón sintético con direcciones pasaron a un spec posterior, y también quedó para después **buscar domicilios por nombre** (hoy es por RUT o apellido). Hoy las direcciones se registran solo desde la ficha. Los specs ya cerrados no se editan; cada cambio de numeración queda en el spec siguiente. Un ajuste decidido al implementar se anota en el mismo spec (paso y decisiones), marcado «Ajustado al implementar». Ojo: el spec 01 declara dentro de su alcance un bloqueo temporal tras intentos fallidos de login, que **no está implementado** en el código (ni middleware, ni librería).

## Arquitectura

- `farmacia_turnos/`: configuración. Tres apps montadas en la raíz: `cuentas` (`path("", include("cuentas.urls"))`, el login vive en `/`), `turnos` y `reparto`. `ALLOWED_HOSTS` y `CSRF_TRUSTED_ORIGINS` salen de `hosts_locales(TURNOS_HOSTS_LOCALES)`: sin la variable quedan vacíos (Django acepta localhost con `DEBUG`); con IP de la red local agrega esas IP, `https://<ip>:8443` y también localhost, que Django deja de aceptar solo si la lista no está vacía. `django_extensions` (de `requirements-dev.txt`) entra a `INSTALLED_APPS` solo si está instalado.
- **Usuario propio** (`cuentas.Usuario`, `AUTH_USER_MODEL`): el **RUT reemplaza al username** (`USERNAME_FIELD = "rut"`). Se guarda normalizado (`12345678-5`, sin puntos, K mayúscula). Toda entrada de RUT pasa por `cuentas/validators.py` (`normalizar_rut` + `validar_rut` con módulo 11); el login (`LoginRutForm.clean_username`) normaliza antes de buscar, y `UsuarioManager.create_user` hace lo mismo. Cambiar `AUTH_USER_MODEL` después de migrar obliga a borrar la BD.
- **Roles** (`Rol`): `qf` (Química Farmacéutica, administradora), `funcionario` y `encargado_terreno`. `inicio` redirige por rol: QF a la gestión de usuarios, funcionario al panel de atención (`turnos:atencion`) y Encargado de Terreno a los domicilios (`reparto:domicilios`, spec 06; la página de marcador de posición `panel_funcionario` quedó sin uso). `Usuario.puede_atender` es verdadero para funcionario y QF; `es_encargado_terreno` y `puede_consultar_domicilios` (Encargado y QF) sirven a los mixins de `reparto` y a la barra. `SoloQF` (`cuentas/mixins.py`) protege las vistas de administración de cuentas y de ventanillas con 403 para otros roles; `SoloAtencion` (`turnos/mixins.py`) protege el panel de atención, la consulta de recetas, la preparación y los preparados (funcionario y QF; el Encargado de Terreno recibe 403). `SoloQF` también protege el padrón. En `reparto/mixins.py`, `SoloTerreno` (solo el Encargado de Terreno: registrar, editar, verificar, fotos) y `ConsultaDomicilios` (Encargado y QF: lista, ficha y fotos); el funcionario recibe 403. La gestión de cuentas se hace en vistas propias, no en el admin de Django.
- **Cambio de contraseña obligatorio:** `Usuario.debe_cambiar_password` (por defecto `True`) activa el middleware `CambioPasswordObligatorio`, que redirige a `/cambiar-password/` todo lo que no sea esa ruta, el logout o `STATIC_URL`. La QF crea cuentas con contraseña inicial y la resetea con `UsuarioResetearPasswordView`, que vuelve a activar la bandera. Toda ruta nueva queda bloqueada por este middleware hasta que el usuario cambie su clave.
- **App `turnos`** (spec 02). Modelos en `turnos/models.py`: `Paciente` y `RecetaCronica` (simulan Rayén, sin integración real), `Ventanilla` (`funcionario` uno a uno = quién la tiene abierta) y `Turno`. Número `G-045`/`P-012`/`U-003`: letra por categoría y correlativo diario por letra. Dos restricciones únicas en `Turno` hacen cumplir en la base que no haya números repetidos ni dos turnos activos del mismo RUT el mismo día.
  - `servicios.py`: la lógica de negocio. `emitir_turno` (deduce la categoría desde `Paciente`; devuelve `EMITIDO`/`VIGENTE`/`DOMICILIO`/`BLOQUEADO`; con `desde_panel=True` es la urgencia, que anula el turno en espera del mismo RUT), `llamar_siguiente`, `re_llamar`, `iniciar_atencion`, `finalizar_atencion` (suma la entrega a la receta), `marcar_ausente` (el servidor exige `TURNOS_SEGUNDOS_MINIMOS_AUSENTE` desde el último llamado), `abrir_ventanilla`, `terminar_turno_de_ventanilla`, `resumen_cola` y `obtener_estado_sala` (spec 03, solo lectura: los 5 últimos llamados del día, del más reciente al más antiguo). Los errores esperables son `ErrorDeAtencion` y su mensaje se muestra al funcionario tal cual.
  - `motor.py::elegir_siguiente(fecha)`: urgencia primero; luego 2 generales por cada preferencial (`TURNOS_GENERALES_POR_PREFERENCIAL`), calculado desde los llamados del día sin contador guardado; dentro de cada categoría, orden de emisión. No modifica datos.
  - Concurrencia sin `select_for_update` (no hace nada en SQLite): `UPDATE` condicional sobre `estado` + reintento, y restricciones únicas más reintento para el correlativo.
  - Estados: `en_espera → llamado → en_atencion → atendido`, o `ausente` (final: el paciente saca un turno nuevo) y `anulado` (solo por urgencia). Desde el spec 05, `ausente` también se alcanza desde `en_atencion` con «No retiró» (`registrar_no_retiro`, sin plazo): el paciente se fue antes de recibir sus medicamentos.
  - **Preparación** (spec 05, HU-17 y HU-18): `Preparacion`, uno a uno con `Turno` (`turno.preparacion`), con su propio ciclo `EstadoPreparacion`. `iniciar_atencion` la crea en la misma transacción (`en_preparacion`: es la recepción); `marcar_lista` la pasa a `lista` (desde `/preparacion/`); `finalizar_atencion` **exige** `lista` y la deja `entregada`; `registrar_no_retiro` la deja `pendiente_retiro` si estaba lista o `anulada` si no; `entregar_pendiente` (desde `/preparados/`) la pasa de `pendiente_retiro` a `entregada` y suma la entrega solo si la receta tiene entregas disponibles (si no, `ErrorDeAtencion` y sigue pendiente). Todo con `UPDATE` condicional sobre `estado`. Reglas: `lista_en` es la fecha original de preparación y no cambia; una preparación `entregada` con `no_retirada_en` es un retiro posterior (el dato que necesitará HU-20); un turno `en_atencion` sin preparación (anterior al spec o editado en el admin) se finaliza como antes. `preparaciones_del_dia` arma la pantalla de preparación (urgencias primero) y `preparados_pendientes(busqueda)` busca por RUT o por parte del apellido sin tildes (filtra en Python: SQLite no compara sin tildes).
  - **Espera estimada** (`turnos/estimacion.py`, spec 05): `(turnos_por_delante + turnos en curso) × promedio_de_atencion ÷ ventanillas abiertas` (habilitadas y con funcionario), redondeado hacia arriba a `TURNOS_MINUTOS_REDONDEO_ESPERA`. `estimar_espera` devuelve 0 para «menos de 5 minutos» y `None` sin estimación (menos de `TURNOS_MUESTRAS_MINIMAS_ESPERA` atenciones con preparación en `TURNOS_DIAS_HISTORIAL_ESPERA` días, sin ventanillas abiertas o turno que no está en espera). El promedio es de la atención completa (`inicio_atencion_en` a `cierre_en`), no solo de la preparación. `turnos_por_delante` **simula** el orden de `elegir_siguiente` sin tocar `motor.py` (usa `_generales_seguidos`); `test_estimacion` compara los dos órdenes, así que si cambias el motor, esa prueba avisa. Se calcula al mostrar el ticket (`totem_turno`, solo `EMITIDO` y `VIGENTE`), sin guardar nada.
  - Rutas: `/totem/` (público, sin login), `/atencion/` (panel; sus acciones son POST bajo `/atencion/...`, y `/atencion/cola/` entrega el fragmento de la fila y `/atencion/preparacion/` el del estado de la preparación), `/ventanillas/` (solo QF), `/sala/` y `/sala/estado/` (públicas, solo GET), `/padron/...` (solo QF), y `/recetas/`, `/preparacion/...` y `/preparados/...` (funcionario y QF, con `SoloAtencion`). Constantes `TURNOS_*` al final de `settings.py`.
  - **Sala de espera** (spec 03): `/sala/` incrusta la instantánea con `json_script` y `/sala/estado/` (`SalaEstadoView`) entrega la misma en JSON. Contrato fijo, que cuidan pruebas de claves exactas: `fecha`, `servidor_en`, `actual` (= `recientes[0]` o `null`) y `recientes`; cada llamado lleva solo `turno_id`, `numero`, `ventanilla` (`Ventanilla.numero`), `veces_llamado` y `ultimo_llamado_en`. Las horas van en hora de Santiago con milisegundos. Nunca agregues RUT, paciente, estado ni categoría: es una pantalla pública. Entra todo turno del día con ventanilla y `ultimo_llamado_en` que no esté `en_espera` ni `anulado`; un re-llamado sube al turno sin duplicarlo. La sala no escribe en la base.
  - **Padrón** (spec 04): pacientes y recetas entran por la importación de un archivo exportado de Rayén (`.csv` con `;` o `,`, en UTF-8 o Windows-1252, o `.xlsx`), que la QF sube en `/padron/`. El admin de Django queda como acceso técnico para correcciones puntuales. `turnos/importacion.py` hace todo: `leer_archivo` (lanza `ErrorDeArchivo` si el archivo no sirve entero), `validar_filas` (pura, motivos 1 a 6 del spec), `planificar` (compara con la base por lotes, sin escribir; motivo 7: el folio ya es de otro RUT), `preparar_carga` (crea el `CargaPadron` `pendiente` con `filas_validas` en JSON: es la vista previa) y `confirmar_carga` / `cancelar_carga` / `descartar_cargas_vencidas` (lanzan `ErrorDeCarga`). Reglas que no se deben romper:
    - El paciente se identifica por RUT y la receta por `RecetaCronica.folio`, que es único y nulo: las recetas creadas a mano no lo llevan, y la importación lo exige. La renovación médica es una receta con folio nuevo.
    - La carga solo crea y actualiza; nunca borra ni desactiva lo que no viene en el archivo.
    - `entregas_realizadas` nunca baja: queda en el mayor entre el valor local y el del archivo, y la confirmación lo escribe con `Greatest(F(...), valor)` para respetar una entrega registrada entre la vista previa y la confirmación.
    - Confirmar toma la carga con un `UPDATE` condicional `pendiente → aplicando`, vuelve a comparar con la base y escribe todo en una transacción. Si falla, la carga vuelve a `pendiente`. Pasados `TURNOS_PADRON_MINUTOS_PENDIENTE` sin confirmar, la carga se descarta.
    - El archivo subido no se guarda: quedan su nombre, tamaño y huella SHA-256, quién lo subió, los conteos, los rechazos y las advertencias. `filas_validas` se borra al aplicar, cancelar o descartar. Paciente y receta apuntan a la última carga que los creó o modificó (`carga`).
    - Los CSV que se descargan (plantilla y rechazos) usan `csv_para_excel`: `;`, UTF-8 con BOM y `neutralizar_celda` (antepone `'` a lo que empieza con `=`, `+`, `-` o `@`).
  - **Avance de la receta** (spec 04, HU-21): `RecetaCronica.entrega_en_curso`, `entregas_restantes` y `estado` (`vigente`, `vencida` o `agotada`). El turno en curso del panel muestra «Entrega N de M» y el vencimiento. `/recetas/` busca por RUT **por POST**, para que el RUT no quede en la URL ni en el historial del equipo compartido.
- **App `reparto`** (spec 06, HU-12): el domicilio de cada paciente con despacho a domicilio (`Paciente.es_despacho_domicilio`: postrado o mayor de 80). Modelos en `reparto/models.py`: `Domicilio` (uno a uno con `Paciente`, `PROTECT`; `Sector` Verde, Azul o Rojo; dirección, referencias, latitud y longitud con 6 decimales; `EstadoDomicilio` `pendiente` o `verificado`, con quién y cuándo), `FotoDomicilio` y `CambioDomicilio` (historial: quién, cuándo, `AccionDomicilio` y cómo quedó en `datos`, más el motivo). Un paciente con despacho sin `Domicilio` está «sin dirección» (no es un estado). Reglas en `reparto/servicios.py` (lanzan `ErrorDeDomicilio`, que se muestra tal cual):
    - `guardar_domicilio` crea o edita y deja un cambio (sin cambios no escribe). `verificar` **exige coordenadas**; editar un verificado **lo deja verificado**, pero no se le pueden borrar las coordenadas; para pedir otra verificación está `marcar_pendiente`, con motivo obligatorio. Los cambios de estado son `UPDATE` condicionales sobre `estado`.
    - Un domicilio con historial no se puede borrar (`PROTECT`): es a propósito.
    - `leer_coordenadas` acepta punto o coma decimal y «lat, lon» pegado; en el formulario, las dos pegadas en la latitud **mandan sobre la longitud**. `static/js/reparto.js` repite la regla (`leerCoordenadas`, `puntoDeLosCampos`) para el mapa; el servidor es quien valida.
    - `pacientes_con_despacho()` aplica en la base el mismo criterio que `es_despacho_domicilio` (con el borde del 29 de febrero). `resumen_de_verificacion()` es el indicador IG04: verificados sobre registrados, y aparte los sin dirección.
    - **Fotos:** hasta `REPARTO_FOTOS_MAXIMAS`. `procesar_foto` revisa peso y píxeles antes de cargar la imagen, aplica la orientación del EXIF, achica a `REPARTO_PIXELES_LADO_MAYOR` y guarda un JPEG **sin metadatos** con nombre aleatorio; el original no se guarda. Van a `MEDIA_ROOT` (`media/`, ignorado por git), que **no tiene URL pública** (no hay `MEDIA_URL` servida): `reparto:foto` las entrega con permisos y `Cache-Control: private`. Borrar elimina el archivo al confirmarse la transacción.
    - Rutas: `/domicilios/` (lista: filtros de sector y estado por GET, búsqueda por RUT o apellido por POST), `/domicilios/<paciente_id>/` (ficha) y sus acciones POST (`editar/`, `verificar/`, `pendiente/`, `fotos/`), `/domicilios/fotos/<pk>/` y `.../borrar/`. La ficha de un paciente sin despacho y sin domicilio da 404. Constantes `REPARTO_*` al final de `settings.py`.
    - La importación del padrón **no trae domicilios**: salió del spec 06 hacia uno posterior. La búsqueda de la lista es por RUT o apellido (`pacientes_de_despacho`), no por nombre.
- **Sesión:** política pensada para un equipo compartido en el mesón (30 min de inactividad, renovada en cada request, cierre al cerrar el navegador). Ver el final de `settings.py`. La renovación en cada request la hace `cuentas.middleware.SesionPorActividad` (subclase de `SessionMiddleware`, en lugar del de Django): las vistas marcadas con `cuentas.mixins.SondeoAutomatico` (hoy `ColaView`, el sondeo de la fila; `SalaEstadoView`, el de la sala; `PreparacionFilaView`, el de la pantalla de preparación, y `AtencionPreparacionView`, el del estado de la preparación en el panel) **no** renuevan la sesión salvo que el navegador envíe la cabecera `X-Actividad-Reciente: 1`, que `panel.js` manda solo si hubo clic, tecla, toque o movimiento en los últimos `TURNOS_SEGUNDOS_ACTIVIDAD_RECIENTE` segundos. Sin eso, un panel olvidado nunca vencería. Cualquier vista nueva que consulte sola al servidor debe usar ese mixin.

## Frontend

Plantillas Django sin build step. `templates/base.html` es la base (bloques `titulo`, `estilos` (hojas propias de una página, antes de `estilos.css`), `clase_body`, `clase_contenido`, `scripts`, `barra`, `contenido`, `pie`; el tótem vacía `barra` y `pie`, y el panel agrega `contenido--ancho`); la navegación de la barra depende del rol; las plantillas de cada app viven en `<app>/templates/<app>/`. Los campos de formulario se renderizan con `templates/includes/campo.html` (añade el botón mostrar/ocultar a los campos de contraseña).

- **Alpine.js 3.14.9** está copiado en `static/js/alpine.min.js` (no se usa CDN: el CESFAM puede estar sin internet). Su lógica vive en componentes `Alpine.data` con nombre: `static/js/comun.js` (`envio`, `modalConfirmacion`; se carga en todas las páginas), `static/js/totem.js` (`teclado`, `reinicio`), `static/js/panel.js` (`turnoLlamado`, `filaEnVivo`, `preparacionEnVivo`), `static/js/sala.js` (`salaEnVivo`) y `static/js/reparto.js` (`mapaDomicilio`, `mapaDomicilios`, `ubicacionActual`, `copiarTexto`). Las plantillas solo los invocan (`x-data="teclado({ inactividad: 30 })"`). Esos archivos se cargan **antes** de Alpine (`comun.js` y luego el bloque `scripts` de `base.html`; Alpine arranca en cuanto se ejecuta) y registran sus componentes al evento `alpine:init`. El único otro JS es **Leaflet 1.9.4**, copiado en `static/vendor/leaflet/` con su licencia (verificado contra la huella del registro de npm), que las páginas de domicilios cargan antes de `reparto.js`.
- **Sondeo en `panel.js`:** `filaEnVivo` reemplaza todo el fragmento en cada consulta; sirve solo para contenido sin modales ni foco (la fila del panel y la pantalla de preparación, cuyo «Marcar lista» no usa modal). No reemplaces un fragmento con botones que abren el modal de confirmación: el modal guarda el formulario y, si ya no está en la página, `requestSubmit()` no envía nada (y `{% csrf_token %}` cambia en cada respuesta, así que no se puede comparar el HTML). Por eso `preparacionEnVivo` reemplaza solo el fragmento del estado (`_preparacion_turno.html`, con `data-estado`), deja «Finalizar» y «No retiró» fijos, los habilita o cambia su texto (`data-confirmar-texto-lista`) al ver «lista», y deja de consultar. Las dos comparten `rastrearActividad` y `pedirFragmento`.
- **`sala.js`** va entero en una IIFE. Arriba están las funciones puras, sin DOM ni Alpine: `identificador`, `llamadosNuevos` (qué anunciar: identificadores que no estaban en la última instantánea recibida con éxito y dentro de `TURNOS_SEGUNDOS_VIGENCIA_ANUNCIO`, según dos horas del servidor), `textoDelAnuncio` y `elegirVoz`. Se exportan con `module.exports` solo si existe `module`, y el componente se registra solo si existe `document`, así Node carga el mismo archivo. `salaEnVivo` sondea con `setTimeout` encadenado (nunca dos consultas en curso, aborto a los 5 s, espera doble sin conexión hasta el tope) y nunca envía `X-Actividad-Reciente`. La instantánea incrustada es la línea base: al cargar no se anuncia nada. El `AudioContext`, la cola de anuncios y la bandera "sonando" viven en la clausura del componente, no en su estado reactivo. La elección de voz se guarda en `localStorage` (`sala:voz`, siempre dentro de `try/catch`). Al recargar con la voz activa se crea el `AudioContext`: si queda suspendido y no hubo interacción, se pide «Toque la pantalla para reactivar la voz» (en modo kiosco queda en `running` y no se pide). La reactivan `pointerup`, `touchend` y `keydown`, que son los eventos que el navegador cuenta como interacción (en pantalla táctil, al soltar el dedo).
- **Mapa del domicilio** (`reparto.js`, spec 06): teselas de OpenStreetMap (`tile.openstreetmap.org`, **sin clave**) con la atribución siempre visible. Las tres páginas (lista, ficha y formulario) comparten `reparto/_mapa.html` (lienzo, avisos y botones propios de acercar, alejar y «Mostrar mi ubicación»; sin los controles de Leaflet). `mapaDomicilios` pone en la lista un marcador por domicilio con coordenadas (llegan con `json_script`): al pasar o enfocar una fila (`data-paciente`) su marcador se destaca, y tocar un marcador abre la ficha. `mapaDomicilio` muestra en la ficha el marcador con la placa de la dirección (tomada de `data-placa`, como texto) y, en el formulario, mantiene iguales el marcador y los campos de latitud y longitud en los dos sentidos (tocar el mapa o arrastrar el marcador llena los campos; escribirlos lo mueve). El mapa y el marcador viven en la clausura, no en el estado de Alpine. Los marcadores son `L.divIcon` con una gota (`.pin`, pendiente punteada y verificado llena); las animaciones van en `.pin` porque Leaflet mueve `.pin-icono`. Al cargar, `volarA` lleva la cámara desde la vista guardada en `sessionStorage` (`reparto:vista`, en `try/catch`) dejando libre el ancho de la hoja flotante, y recién al llegar cae el marcador; con `prefers-reduced-motion`, todo queda en su lugar sin animar. Si las teselas no cargan, muestra un aviso y el formulario sigue: **lo que se guarda son siempre los campos**. La capa de teselas lleva `referrerPolicy: 'strict-origin-when-cross-origin'`: **no la quites**. Django envía `Referrer-Policy: same-origin` en todo el sitio, y sin `Referer` OpenStreetMap responde 200 con la imagen «Access blocked» (Leaflet no lo ve como error, así que el aviso no aparece). Con esa política sale solo el origen, nunca la ruta con el id del paciente. `ubicacionActual` («Usar mi ubicación actual») aparece solo con `window.isSecureContext`: el GPS del navegador exige HTTPS o localhost, de ahí `runserver_plus`. Las coordenadas se muestran con `|unlocalize`: con `es-cl` saldrían con coma decimal y no se distinguirían de la coma que separa las dos.
- **Confirmaciones:** nunca con `confirm()` del navegador. Un formulario que debe confirmarse declara `data-confirmar-titulo` (y opcionales `-texto`, `-accion`, `-cancelar`, `-objeto`, `-peligro`, `-turno`) y se envía con `x-data="envio" @submit="enviar($event)"` (o con `window.confirmarEnvio(evento)` desde otro componente). Eso abre el modal único de `templates/includes/confirmacion.html` (un `<dialog>` incluido en `base.html` para usuarios con sesión): muestra el objeto de la acción en grande, nombra los botones por la acción, deja el foco en la opción segura, se cierra con Esc o clic fuera, devuelve el foco y, al aceptar, reenvía el formulario. Los textos van en atributos HTML (Django los escapa), no dentro de JavaScript.
- **Inicio de sesión:** es la credencial del funcionario (`.credencial`) colgando de su cinta sobre la ilustración del CESFAM; la página no lleva barra ni pie. Al cargar, la credencial cae y se balancea (`credencial-llega`, apagada con `prefers-reduced-motion`): es el único movimiento automático de esa página. El paciente tiene un ticket y el funcionario una credencial: no mezcles los dos objetos.
- **Páginas de la QF (usuarios, ventanillas, padrón), la consulta de recetas, la preparación, los preparados y los domicilios:** usan listas, no tablas (`.lista` con filas `.lista__fila`: datos a la izquierda y acciones como botones de texto `.boton--texto` a la derecha); también los rechazos y advertencias de una carga. Cada acción tiene su columna fija (`.lista--usuarios`, `.lista--ventanillas`, `.lista--cargas`, `.lista--preparacion`, `.lista--preparados`), así queda alineada aunque a una fila le falte una acción. Un formulario de una línea sobre su lista (subir el padrón, buscar recetas, preparados o domicilios) va en `.tarjeta--formulario`; las búsquedas de `/preparados/` y `/domicilios/` también van por POST. Los filtros de `/domicilios/` son enlaces (`.filtros`, el activo con `aria-current`), porque no llevan datos personales. Los conteos de una carga van en `.resumen`. Las insignias de estado de carga (`insignia--pendiente`, `--aplicada`...) de receta (`--vigente`, `--vencida`, `--agotada`) de preparación (`--en_preparacion`, `--lista`) y de domicilio (`--pendiente`, la misma de las cargas; `--verificado`; `--sin_direccion`, que no es un valor del modelo sino la ausencia de domicilio) siguen la misma regla: el valor del modelo como modificador y siempre con texto. Los usuarios activos se agrupan por rol (`GRUPOS_DE_USUARIOS` en `cuentas/views.py`) y los desactivados van en su propia sección al final, para que sigan en el listado. La propia cuenta se marca con "Tu cuenta" y no ofrece "Desactivar" (solo en la interfaz: el servidor aún lo permite). El RUT se muestra con puntos con el filtro `rut_legible` (`{% load rut %}`); se guarda sin ellos.
- **Pruebas de JavaScript:** `pruebas_js/` (fuera de `static/`, así no se sirve ni lo copia `collectstatic`) tiene pruebas con el ejecutor de Node (`node --test "pruebas_js/*.test.js"`). Con Node 21 o superior el argumento es un patrón: `node --test pruebas_js/` ya no recorre la carpeta. Solo cubren funciones puras. Para el comportamiento real (teclado, temporizadores, sondeo, sonido) se usó Edge sin cabeza controlado por el protocolo de DevTools (desde Node, con el `WebSocket` que trae). Sus trampas:
  - **Sin cuadros fiables:** sin pantalla real, Alpine agenda `x-show` con `requestAnimationFrame`. Hay que simular `document.visibilityState = 'hidden'`.
  - **Sin JavaScript:** `--blink-settings=scriptEnabled=false` no genera capturas. Se usa `Emulation.setScriptExecutionDisabled`.
  - **Sin restricción de sonido:** Edge sin cabeza deja sonar sin interacción, así que para probar el aviso de toque hay que emular la política en la página.
  - **Sin voz audible:** solo trae voces en línea, que fallan con `synthesis-failed`. La campanilla y la frase se oyen solo en un Edge normal con parlantes.
  - **Plantillas en caché:** `runserver --noreload` las guarda, y sin reiniciarlo no se ven los cambios.
  - **Rutas convertidas por Git Bash:** un argumento como `/domicilios/` se convierte en una ruta de Windows y la navegación falla («Cannot navigate to invalid URL»). Se ejecuta con `MSYS_NO_PATHCONV=1`.
  - **GPS:** se simula con `Browser.grantPermissions` (`geolocation`) y `Emulation.setGeolocationOverride`; para probar el contexto seguro hay que entrar por HTTPS (con `--ignore-certificate-errors`) o por localhost.
  - **Teselas sin conexión:** `Network.setBlockedURLs` con `*tile.openstreetmap.org*` simula el mapa sin internet.

  `node --check static/js/*.js` valida la sintaxis.
- **CSS** único en `static/css/estilos.css`, ordenado por componentes con un índice al inicio (variables, base, barra, tarjetas, formularios, botones, insignias, avisos, tablas, login, panel, fila, tótem, sala, preparación, domicilios): agrega cada regla en su sección y no al final. Clases en español estilo BEM (`.tarjeta--angosta`, `.boton--secundario`). Los colores están en variables `:root` (`--primario`, `--acento`, ...). El ancla es el verde petróleo (`#1b7a6b`), que contrasta con la ilustración naranja del login y con el amarillo del ticket (texto blanco sobre el primario: 5,2:1). Los grises, la tinta y los fondos tienen el mismo matiz verde: si cambias el primario, deriva toda la familia, incluidos los pocos colores fijos del CSS (sombras, fondo del modal, ranuras). Con daltonismo rojo-verde el primario se ve gris, por eso ninguna insignia ni estado depende solo del color. El rojo y el ámbar son solo para urgencias, errores y advertencias.
- **Identidad visual:** el sistema reemplaza los rollos de papel numerados, así que el protagonista es el número de turno. Reglas que sostienen esa identidad:
  - **Papel de turno** (`--papel`, amarillo; `--papel-claro` para el siguiente): significa "es su turno" y solo se usa en el ticket del tótem, el turno llamado del panel, el siguiente en la fila y el último llamado de la sala de espera (spec 03; sin llamados, esa tarjeta va gris, sin papel). No lo uses para otra cosa.
  - **Forma de ticket** (línea de corte punteada con muescas): solo en el ticket del tótem (`.ticket`, que sale por la ranura del `.dispensador`) y en el turno en curso del panel (`.turno`, con el hueco punteado `.turno--vacio` cuando no hay turno). La sala no la usa, porque no entrega un papel. El resto es sobrio: no la repitas como decoración.
  - **Dos movimientos automáticos:** el ticket saliendo de la ranura (`ticket-sale`) y el pulso del último llamado de la sala (`sala-llamado`, spec 03): 3 pulsos lentos en unos 3 s, bajo el umbral de 3 destellos por segundo. En la sala nadie mira la pantalla cuando llega un llamado, y el pulso atrae la vista aunque la voz esté apagada. La excepción acotada son las páginas de domicilios (spec 06): al llegar a cada una, la cámara del mapa vuela y el marcador cae con una onda, una vez. Todo lo demás se mueve solo como respuesta a una acción; se respeta `prefers-reduced-motion` (en la sala queda solo la etiqueta «Nuevo llamado», que va en texto).
  - **Tipografía:** una sola familia, *Atkinson Hyperlegible Next* (diseñada para baja visión; su cero lleva barra para distinguirlo de la O), autoalojada en `static/fonts/` con su licencia OFL y precargada en `base.html`. Números de turno en peso 800 con cifras tabulares; nada de mayúsculas sostenidas en etiquetas ni textos unidos con punto medio.
  - El ticket impreso queda en negro sobre blanco (`@media print`): las impresoras no imprimen fondos. Lo que solo va en papel lleva `.totem__solo-imprimir` (como «calculada a las HH:MM» de la espera estimada), la contraparte de `.totem__no-imprimir`.
  - El tótem debe caber sin desplazarse: su alto total es ≈49 veces el tamaño base (con un error a la vista), por eso la base es `min(1.95vh, 3.1vw)` y en horizontal el teclado pasa a una segunda columna. Si agregas algo al tótem, vuelve a medir (la línea de espera estimada del spec 05 se midió en el ticket a 1080×1920 y 1920×1080, sin desplazamiento). El fondo del login (`static/img/fondo-login.png`) se activa solo con `{% block clase_body %}pagina-login{% endblock %}`. Las insignias `.insignia--<valor>` usan directamente los valores de `Categoria` y `EstadoTurno` (`insignia--urgencia`, `insignia--en_atencion`...) y siempre llevan texto: el color nunca es el único indicador. El tótem usa `pagina-totem` (texto grande en `em` que sigue al tamaño de pantalla, alto contraste, clases `.totem*` y `.ticket*`, con `@media print` para imprimir el número); el tótem nunca muestra nombre ni RUT. Las tablas van dentro de `.tabla-contenedor` para desplazarse en pantallas angostas.
  - La sala (`pagina-sala`, clases `.sala*`) tampoco debe desplazarse, y se midió a 1920×1080 y 1366×768. En un televisor 16:9 manda el ancho, por eso la base es `min(2.3vh, 1.25vw)`. Las columnas van en proporción 3:2: el último llamado a la izquierda y los anteriores a la derecha. El peor caso de alto es el último llamado y los 4 anteriores con «Nuevo llamado», con «Sin conexión» y un aviso de voz en la barra: con todo eso la barra debe quedar en una línea. Por eso «Actualizado a las HH:MM» va junto al título del último llamado y no en la barra. Si agregas algo a la sala, vuelve a medir. Un número de cuatro cifras (`G-1000`) se achica con los modificadores `--largo`. En la sala, el papel dice *quién* y la **placa de ventanilla** (`--primario-oscuro` con el número en blanco, como el letrero sobre cada mesón) dice *adónde*: es la franja bajo el número del último llamado y `.sala__placa` en cada fila de anteriores, siempre junto a la palabra «Ventanilla». La lista de anteriores tiene siempre 4 filas del mismo alto, así no cambia de forma a medida que llegan los llamados.
- **Domicilios** (`.escenario*`, `.hoja*`, `.pin*`, `.domicilio*`, `.lugar*`, `.sector*`, `.avance*`, sección 17 del CSS): se diseña como se reparte. Las tres páginas usan `pagina-mapa` y `contenido--mapa` (sin pie): el mapa ocupa todo y la **hoja** blanca flota a la izquierda con su propio desplazamiento y un pie pegado abajo (verificar o guardar); bajo 760 px el mapa queda arriba y la hoja debajo. Entre ellas, `@view-transition` (declarado solo en sus plantillas) transforma la hoja y deja quieto el mapa. La lista va **agrupada por sector** (Verde, Azul, Rojo y al final «Sin sector», con los sin dirección), cada grupo con «N de M verificados», y cada fila empieza por la **dirección** (lo que se busca en terreno) y debajo el paciente; toda la fila es el enlace a la ficha. Arriba, una sola barra de avance del IG04. En la ficha, la **placa** petróleo con la dirección va al lado del marcador (`.pin__placa`): es el mismo objeto que la placa de ventanilla de la sala (la placa dice *adónde*); no la uses para otra cosa. En la hoja, la dirección con su sector, «Cómo llegar» con las referencias en letra grande, las fotos (se abren en un `<dialog>`, y la casilla «Agregar foto» sube al elegir), el historial plegado y la verificación al pie; «Marcar pendiente» va plegado en un `<details>` porque es poco frecuente. El sector Rojo se nombra en texto, nunca en rojo (el rojo es solo para urgencias y errores).
- La ficha y el formulario del domicilio se usan en terreno, en un teléfono: se midieron a 360 px sin desplazamiento horizontal (el mapa arriba y la hoja debajo). A 1366 px, la barra de la QF ya ocupa dos líneas (8 enlaces); a 1920 px cabe en una.
- `settings.py` usa `es-cl` y `America/Santiago`.
